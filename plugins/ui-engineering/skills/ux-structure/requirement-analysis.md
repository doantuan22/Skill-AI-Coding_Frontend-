# Requirement normalization

Convert raw requirements into `REQUIREMENT-SPEC.md` before deciding the UX structure. Separate facts from assumptions and questions. Do not derive business policy from a UX preference.

Normalize: product and problem; actors and goals; required features; constraints; confirmed business rules; existing system context; UX-relevant technical constraints; known information; unknowns; assumptions; success conditions; and out-of-scope work.

For an existing system, compare **what exists now** with **what the user requests**. If an API, route, auth, database, or backend rule must change, record it as a dependency rather than treating it as an approved change.
